# Umsetzungsplan MVP

Vertical Slices, jeder Schritt endet mit grünem Linter (`rubocop-rails-omakase`, Default-Config) und grünen Tests (Minitest). TDD für Importer, Upload-API, Login und Autorisierung. Autorisierung über Model-Scopes, ohne zusätzliches Gem. Grundlage: `CONTEXT.md` und `docs/adr/`. Jeder konfigurierbare Wert aus den ADRs wird als Umgebungsvariable mit Default im Schritt eingeführt, der ihn braucht, und getestet.

| # | Schritt | Verify |
|---|---|---|
| 1 | **Skeleton**: `rails new` mit Postgres, ohne Solid Queue und Solid Cable, Solid Cache in der primary-DB (ADR 0001). Dockerfile mit Non-Root-User, `/up` als Healthcheck, Migrationen beim Start, `TMPDIR` auf einem flüchtigen Volume (ADR 0003). Puma-Version gepinnt, `http_content_length_limit` aus Umgebungsvariable (ADR 0004). | `rubocop` ohne Offenses, `rails test` grün, `docker build` und Container antwortet auf `/up`. Test gegen einen echten Puma-Prozess: Body über dem Limit ergibt `413`, mit `Content-Length` und chunked. |
| 2 | **Schema**: `users` (`iss`, `sub`, deaktiviert, Groups und Admin-Flag vom letzten Login), `projects` (Owner User oder Group, Name eindeutig pro Owner, Visibility, Visibility-Group), `owner_quotas` (eine Zeile pro Owner mit Occurrence-Zähler, sperrbar), `repos` (Default Branch, manuell gesetzt ja/nein), `branches`, `artifacts` (Kategorie, Name), `scans` (Branch, Artifact, gemeldeter Artifact-Typ, `ArtifactName`, `SchemaVersion`, `CreatedAt`, `Trivy.Version`, OS, Commit, Tag, Trigger, Service Account, Zähler), `findings` (Project, Fingerprint eindeutig, Typ, Beschreibung), `occurrences` (Version, Fundort, `FixedVersion`, Status, Severity; eindeutig mit `NULLS NOT DISTINCT`), `service_accounts` (Owner), `upload_tokens` (Hash, Pflicht-Ablauf, Widerruf, angelegt von, zuletzt benutzt). | Model-Tests für Unique-Constraints, Pflichtfelder und Enums. Migration läuft hoch und zurück. |
| 3 | **Importer** (reines Ruby-Objekt): Allowlist-Felder lesen (ADR 0003), URLs auf `scheme://host/path` reduzieren, Artifact-Kategorie und Kürzung um Tag und Digest (ADR 0008), Fingerprint pro Typ inklusive os-pkgs, Misconfiguration-ID-Normalisierung, Namespace, nur `FAIL` und Target-Normalisierung (ADR 0002), Occurrences, Zähler mit höchster Severity pro Finding, leeres `Results`. Fixtures aus echten Trivy-Läufen (Image, fs, repo; `--scanners vuln,misconfig,secret,license`, `--show-suppressed`, `--trace`, `--include-non-failures`). | Tests pro Finding-Typ und Normalisierungsregel (Registry-Port, IPv6, `DS005` → `DS-0005`, `builtin.*`). Secret-Test: je ein Marker in `Code`, `ImageConfig`, `Layer.CreatedBy`, `CauseMetadata.Code`, `RenderedCause`, `Traces`, `Message`, ein unbekanntes Feld sowie Userinfo und Query in `ArtifactName`, `PrimaryURL`, `References`, `Link`; kein Marker in DB, Logs oder Response. Upgrade ohne Fix ergibt dasselbe Finding; mehrere Versionen und Fundorte bleiben als Occurrences erhalten und zählen einmal mit höchster Severity; Nicht-`FAIL` wird verworfen; gleicher Report zweimal ergibt keine doppelten Findings. Messung von Dauer und Speicher mit einem großen echten Report; über etwa 10 Sekunden oder zu viel Speicher: Entscheidung nach ADR 0004. |
| 4 | **Upload-API**: `POST` mit Bearer-Token in der Reihenfolge aus ADR 0004: `401` mit `WWW-Authenticate`, `rate_limit` mit `429` und fail-closed `503`, `415`, generische `400`, `422` für k8s und `SchemaVersion`, Import in einer Transaktion mit Sperre auf `owner_quotas` und Quote (`507`), `201` mit `Location` auf die Scan-Route (hier angelegt). `project` wird nur im Namensraum des Service-Account-Owners aufgelöst; Project, Repo und Branch werden bei Bedarf angelegt, neue Projects mit Start-Visibility nach ADR 0007; Default-Branch-Regel nach ADR 0008. Token aktualisiert "zuletzt benutzt". Kein Body und keine Parser-Meldung in Logs. | Request-Tests für jeden Statuscode. Abgelaufene und widerrufene Tokens werden abgelehnt. Token von Owner A mit dem Project-Namen von Owner B legt ein eigenes Project für A an, B bleibt unverändert. Start-Visibility je Owner-Typ. Token öffnet keine andere Route. Paralleler Upload kann die Quote nicht überschreiten. Rollback hinterlässt keinen Scan. Nach Requests mit `201`, `400`, `422` und `507` bleibt kein Tempfile zurück. Log-Test: kein Report-Inhalt. Default Branch: später hochgeladener `main` übernimmt, manuell gesetzter bleibt, gelöschter fällt auf die Regel zurück. |
| 5 | **OIDC-Login** (ADR 0006): `omniauth_openid_connect` mit PKCE, state und nonce, Login-Request nur per POST mit CSRF-Schutz (`omniauth-rails_csrf_protection`), `reset_session` beim Login. User über `(iss, sub)`, Pflicht-Login-Group (Start schlägt ohne fehl), fehlender Claim oder Overage-Marker bricht ab, fehlende Login-Group ergibt `403` mit Deaktivierung, Group-Verlust widerruft dort angelegte Tokens, Admin aus Group oder Claim, Break-Glass-Admins per Umgebungsvariable (umgehen Login-Group und Claim-Abbruch, nicht deaktivierbar), Session maximal 8 Stunden, Deaktivierung pro Request geprüft. `User#deactivate!` widerruft alle Tokens nach ADR 0005. | Tests mit gemocktem OmniAuth für jeden Fall. Deaktivierung widerruft eigene und angelegte Tokens, Reaktivierung stellt keine wieder her, Break-Glass-Admin ist nicht deaktivierbar. Deaktivierter User verliert die laufende Session sofort. GET auf den Login-Request wird abgelehnt. Manueller Login gegen den echten Identity Provider. |
| 6 | **Visibility und Verwaltungsrechte** (ADR 0007): `Project.visible_to(user)` für `user`, `group`, `public` und Admin, Verwaltungsrecht für Owner-User, Mitglieder der Owner-Group und Admins, angewendet auf alle verschachtelten Ressourcen. Nicht sichtbare Projects ergeben `404`. | Test-Matrix User × Visibility × Owner-Typ × Admin über alle Routen (Project, Repo, Branch, Scan, Trend-Daten per ID). Anonymer Zugriff wird abgelehnt, auch bei `public`. Sichtbare, aber nicht verwaltbare Projects lassen keine Verwaltungsaktion zu. Visibility-Group nur aus aktuellen Groups des Owners; nach Group-Verlust bleibt das Project für die Group sichtbar. |
| 7 | **UI: Projektliste** mit Owner, Zählern über die Default Branches und nur Artifacts mit Scan in den letzten 30 Tagen (ADR 0008), Navigation Project → Repo → Branch. | System-Test mit Fixture-Daten. Zähler stimmen mit dem letzten Scan überein, verwaiste Artifacts fallen heraus. |
| 8 | **UI: Trend** pro Branch und Artifact, gestapelt nach Severity, umschaltbar pro Finding-Typ, Filter für den Zeitraum. | Test auf die Datenabfrage: eine Serie pro Artifact, keine Vermischung. Sichtprüfung im Browser. |
| 9 | **UI: Scan-Detail und Diff** zum Predecessor (beim Lesen bestimmt), "neu" und "nicht mehr gemeldet", Links nur für `http(s)`-URLs (ADR 0003), hochladender Service Account sichtbar. | Diff zweier Scans mit bekannten Unterschieden, erster Scan zeigt "alles neu". Predecessor ignoriert fremde Branches und Artifacts, ordnet bei gleichem Upload-Zeitpunkt nach ID und wird nach dem Löschen eines Scans neu bestimmt. XSS-Test: `javascript:`-URL wird als Text dargestellt. |
| 10 | **Verwaltung**: Service Accounts für User und Groups, Tokens (Pflicht-Ablauf bis zum Maximum, Klartext einmalig, Widerruf, angelegt von, zuletzt benutzt), Visibility und Default Branch, Löschen von Project, Repo und Branch (Name eintippen) und einzelnen Scans inklusive Anpassung des Quota-Zählers. Admin: User deaktivieren und reaktivieren über `User#deactivate!`. | Tests: fremde Group wird abgelehnt, Klartext-Token danach nirgends abrufbar, Ablauf über dem Maximum wird abgelehnt, Löschen entfernt verwaiste Findings und senkt den Quota-Zähler, gelöschter Default Branch fällt auf die Regel zurück. |
| 11 | **End-to-End und README**: Container gegen echtes Postgres, echter Trivy-Lauf, Upload per `curl`, Ansicht in der UI. README mit CI-Beispielen für GitLab, GitHub, Bamboo und Woodpecker (inklusive Tag-Scans auf dem Default Branch, `--scanners`, `--list-all-pkgs=false`, `trivy fs .`), allen Umgebungsvariablen mit Defaults und Betriebsvoraussetzungen (Ingress-Limits, `ephemeral-storage`, flüchtiges `TMPDIR`-Volume, Login-Group, stabile Group-Werte, Break-Glass-Admins, Offboarding). | Manueller Durchlauf von Upload bis Ansicht. |
